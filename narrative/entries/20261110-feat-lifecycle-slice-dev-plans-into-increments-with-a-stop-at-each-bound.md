## Context

The developer phase went straight from the accepted design to one plan and one build. On large features that made the plan PR hard to review, made long detailed plans harder for a small local model to execute, and gave the build no point where it could safely stop while leaving something working. Splitting detailed plans by layer (domain / application / infrastructure / API / web) made this worse, because nothing worked end to end until the last layer was done.

## Decision

Slice every feature by behaviour into increments that can each be deployed on their own, and run the build one increment per session with a stop at each boundary ("pencils down"). Small features are exempt below a threshold of about eight tasks. Rejected alternative: giving each increment its own build phase, PR and gate. That would mean changing the phase model in `feature.mjs` and the sub-issues, so for now the increment boundary is a checkpoint within the single dev-build phase.

## Consequences

Plans get an increment table, and plan reviews also approve the build order. Builds take more sessions, but each one leaves the system working. Increment boundaries are enforced through the skill and the exit criteria, not by the gate script, so that is left open: if it proves too loose, per-increment gating is the follow-up.
